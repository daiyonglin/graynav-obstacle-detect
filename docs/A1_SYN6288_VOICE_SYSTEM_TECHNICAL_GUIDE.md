# A1-SYN6288 导盲语音播报系统技术说明

## 1. 系统概述

### 1.1 建设目标

A1-SYN6288 导盲语音播报系统是 GrayNav 盲人避障设备的人机交互出口。它将摄像头、目标检测、目标跟踪、测距和避障规划产生的机器状态，转换为盲人能够立即执行的短语音指令。

视觉算法按帧工作，每秒会产生多次检测和决策；语音模块则按句播放，一条语音需要数百毫秒。如果把每一帧中的全部目标、类别和距离逐条播报，语音必然落后于真实环境。因此，本系统不播报冗长的环境描述，而是将所有感知结果压缩为六种行动语义：

- `直行`：当前通行方向安全；
- `减速`：存在中等风险或感知结果不够确定；
- `停下`：前方存在紧急风险；
- `左转`：左侧通行走廊已验证安全；
- `右转`：右侧通行走廊已验证安全；
- `异常`：摄像头、图像、推理或系统资源状态异常。

这种设计把语音模块定位为“行动指令执行器”，而不是“检测结果朗读器”。目标是降低认知负担、控制播报延迟，并保证紧急状态下只输出当前最有价值的信息。

### 1.2 系统数据链路

完整链路如下：

```text
SC132GS 单通道灰度相机
    -> A1 图像采集与双 ROI 预处理
    -> A1 NPU 执行 YOLOv8n-B3 单通道检测
    -> CPU 完成 DFL 解码、NMS 和多目标跟踪
    -> CPU 完成距离估计、TTC 和通行走廊分析
    -> AvoidancePlanner 生成 AvoidanceDecision
    -> VoiceNotifier 提取最新行动
    -> UART0 封装并发送 SYN6288 固定语音帧
    -> 1.8 V/3.3 V 电平转换
    -> SYN6288 合成语音
    -> 功放和扬声器播报
```

视觉、OSD 和语音并行工作。Aurora 继续显示目标框、行动和风险区域，语音线程独立发送行动指令，不占用 Aurora 使用的 CH347 调试串口。

## 2. 总体软件架构

语音相关软件分为四层。

### 2.1 感知层

感知层由目标检测和多目标跟踪组成，输出稳定目标列表。每个目标包含：

- 完整画面坐标框；
- 原始 ROD25 类别和导航语义类别；
- 检测置信度与目标质量；
- 左、中、右或宽目标区域；
- 轨迹编号和连续命中信息。

感知层不直接发送语音，避免单帧误检直接改变用户行动。

### 2.2 测距与规划层

测距层为每条稳定轨迹估计前向距离、横向位置、安全距离下界、接近速度和 TTC。避障规划器再把目标投影到左、中、右三个通行走廊，综合判断哪个方向可以通行。

规划层输出统一结构 `AvoidanceDecision`，其中 `action` 是语音模块使用的核心字段，`prompt` 保存产生该动作的原因，三个 `ZoneStatus` 保存各走廊占用状态。

### 2.3 语音调度层

`VoiceNotifier` 接收高频 `AvoidanceDecision`，完成：

1. 将内部动作映射为中文短词；
2. 只保留最新动作，不积压历史指令；
3. 在独立线程中控制发送节奏；
4. 对相同动作周期重复播报；
5. 对异常状态执行独占和恢复滞回；
6. 记录发送次数、完成次数和 UART 状态。

### 2.4 物理输出层

物理输出层由 A1 UART0、双向电平转换、SYN6288、功放和扬声器组成。A1 只发送数字指令帧，中文语音合成由 SYN6288 完成。

## 3. 硬件连接设计

### 3.1 UART0 引脚

当前系统使用 A1 P4 扩展接口上的 UART0：

| P4 引脚 | A1 信号 | 信号方向 | 外部连接 |
|---|---|---|---|
| 15 | `A1_D0_UART0TX` | A1 -> 外设 | 电平转换低压侧输入，转换后接 SYN6288 `RXD` |
| 16 | `A1_D2_UART0RX` | 外设 -> A1 | 电平转换低压侧输出，另一侧接 SYN6288 `TXD` |
| 33/34/47/48 任一 | GND | 公共参考 | A1、电平转换模块、SYN6288 共地 |

信号必须交叉连接：发送端 TX 接接收端 RX，接收端 RX 接发送端 TX。

### 3.2 电平转换

A1 外设逻辑电平为 1.8 V，语音模块 UART 为 3.3 V。直接连接可能导致：

- SYN6288 无法稳定识别 A1 的高电平；
- SYN6288 的 3.3 V TX 超过 A1 IO 允许范围；
- 长时间运行时产生不可预测的通信错误或 IO 损伤。

因此 TX 和 RX 均通过双向电平转换模块：

```text
A1 1.8 V TX -> LV 通道 -> HV 通道 -> SYN6288 3.3 V RX
A1 1.8 V RX <- LV 通道 <- HV 通道 <- SYN6288 3.3 V TX
```

电平转换模块的 LV 参考电压接 1.8 V，HV 参考电压接 3.3 V。所有模块必须共地，否则 UART 电压没有统一参考。

### 3.3 供电与音频输出

SYN6288 及功放按照载板说明单独供电。P4 的 1.8 V 只作为逻辑侧参考，不承担语音功放供电。电源应保证播放瞬间的电流需求，扬声器阻抗和功率应符合模块输出规格。

### 3.4 串口参数

正式配置为：

```text
baud rate : 9600
data bits : 8
parity    : none
stop bits : 1
flow ctrl : none
```

即 9600 8N1。当前系统不使用 BUSY GPIO，语音节奏由软件事务定时和 UART RX 状态消费共同管理。

## 4. 避障策略如何形成语音指令

### 4.1 通行走廊模型

系统不以“检测到了什么类别”作为唯一决策依据，而是关注障碍物是否侵入用户前进空间。完整画面通过测距结果映射到地面坐标，并划分为：

- 左侧候选走廊；
- 中央主通行走廊；
- 右侧候选走廊。

每条走廊维护：

- 是否被可靠目标占用；
- 最近安全距离；
- 最小 TTC；
- 最近目标的类别和风险权重；
- 当前视图是否已完成有效观测。

目标横向位置小于约 -0.35 m 进入左走廊，大于 0.35 m 进入右走廊，其余进入中央走廊。横跨大范围的可靠目标可同时影响多条走廊。

### 4.2 风险等级

规划器优先使用保守安全距离 `z_safe`，而不是距离均值：

```text
z_safe = estimated_distance - distance_sigma
```

风险划分：

| 条件 | 风险等级 |
|---|---|
| `z_safe < 0.80 m` 或 `TTC < 1.5 s` | urgent |
| `0.80 <= z_safe < 1.05 m` | near |
| `1.05 <= z_safe < 2.00 m` | warning |
| `z_safe >= 2.00 m` | far |
| 无可靠距离 | unknown |

测距不确定并不等价于安全。低质量目标会触发保守的 `slow`，但不会用不可信米数直接触发错误转向。

### 4.3 行动生成规则

| 行动 | 主要条件 | 安全含义 |
|---|---|---|
| `stop` | 中央近障且左右未验证安全；可靠宽近障；中央 TTC 极短 | 立即停止继续前进 |
| `turn_left` | 中央或右侧被阻塞；左侧已验证安全；左侧净空明显更大 | 向左调整方向 |
| `turn_right` | 与左转对称 | 向右调整方向 |
| `slow` | warning、侧边近障、距离或类别不确定 | 降低行进速度并继续观察 |
| `clear` | 中央走廊连续确认安全 | 保持直行 |
| `system_fault` | 摄像头、图像、推理或资源异常 | 停止依赖当前导航结果并检查设备 |

转向提示必须满足候选侧净空大于 1.35 m，并且比另一侧至少多 0.25 m。双 ROI 需要在 500 ms 内均有有效观测，侧方走廊才被视为“已验证”。如果侧方安全性不明确，系统输出减速或停下，而不会冒险提示转向。

### 4.4 动作稳定状态机

动作状态机抑制帧间抖动：

- `stop` 和 `system_fault` 属于最高安全状态；
- `slow` 是风险升级，可快速生效；
- 普通方向动作至少连续两次确认；
- 左右方向反转需保持 300 ms；
- `clear` 需保持 700 ms 才生效；
- 从 `stop` 退出至少保持 500 ms。

状态机先把视觉结果稳定成行动，再交给语音线程。语音线程不重新解释检测框，保证 OSD、串口和语音使用同一个行动来源。

## 5. 动作与中文短语映射

| 内部动作 | 中文短语 | 设计原因 |
|---|---|---|
| `clear` | 直行 | 明确表示保持当前方向 |
| `slow` | 减速 | 两个汉字，响应快且含义明确 |
| `stop` | 停下 | 比单字“停”更完整，仍保持短时长 |
| `turn_left` | 左转 | 明确给出方向动作 |
| `turn_right` | 右转 | 明确给出方向动作 |
| `system_fault` | 异常 | 四类系统故障的统一短告警 |

语音中不加入“前方有人”“距离一米”等信息。类别和距离继续显示在 OSD/串口，语音只传递当前应执行的动作。

## 6. SYN6288 协议帧设计

### 6.1 文本合成帧结构

```text
┌──────┬────────┬────────┬──────┬────────┬──────────────┬──────┐
│ 0xFD │ LEN_H  │ LEN_L  │ CMD  │ PARAM  │ GBK_TEXT...  │ XOR  │
└──────┴────────┴────────┴──────┴────────┴──────────────┴──────┘
```

字段定义：

- `0xFD`：固定帧头；
- `LEN_H/LEN_L`：数据区长度，高字节在前；
- `CMD=0x01`：文本语音合成；
- `PARAM=0x01`：GBK 编码，无背景音乐；
- `GBK_TEXT`：待播报中文的 GBK 字节；
- `XOR`：从帧头开始到文本末尾的逐字节异或校验。

对于四字节 GBK 文本，数据区由命令 1 字节、参数 1 字节、文本 4 字节、校验 1 字节组成，因此长度为 7，即 `00 07`。

### 6.2 校验码计算示例

“停下”的 GBK 为：

```text
停 = CD A3
下 = CF C2
```

校验码：

```text
FD XOR 00 XOR 07 XOR 01 XOR 01 XOR CD XOR A3 XOR CF XOR C2 = 99
```

最终帧：

```text
FD 00 07 01 01 CD A3 CF C2 99
```

### 6.3 正式固定帧

| 动作 | 完整帧 |
|---|---|
| 直行 | `FD 00 07 01 01 D6 B1 D0 D0 9D` |
| 减速 | `FD 00 07 01 01 BC F5 CB D9 A1` |
| 停下 | `FD 00 07 01 01 CD A3 CF C2 99` |
| 左转 | `FD 00 07 01 01 D7 F3 D7 AA A3` |
| 右转 | `FD 00 07 01 01 D3 D2 D7 AA 86` |
| 异常 | `FD 00 07 01 01 D2 EC B3 A3 D4` |

固定帧在编译期保存为 `std::vector<uint8_t>`，运行时根据动作直接选择，避免动态字符编码、字符串转换和临时缓冲区带来的不确定性。

### 6.4 UART 回传状态

工作线程持续读取并消费 SYN6288 回传字节：

| 状态码 | 协议含义 | 系统用途 |
|---|---|---|
| `0x41` | 命令接收 | 通信统计与诊断 |
| `0x45` | 帧接收状态异常 | 通信统计 |
| `0x4A` | 模块初始化完成 | 模块状态观测 |
| `0x4E` | 模块正在播放 | 播放状态观测 |
| `0x4F` | 模块空闲 | 播放状态观测 |

正式运行以确定性发送节拍和短语时长控制下一次发送，RX 通道用于持续清空接收 FIFO、记录模块状态和辅助诊断。这样无需 BUSY GPIO，也不会让 RX 数据长期堆积。

## 7. A1 UART 驱动实现

### 7.1 初始化

`VoiceNotifier::InitializeFromEnv()` 完成：

1. 读取运行模式和语音参数；
2. 初始化 A1 GPIO 控制句柄；
3. 把 D0/D2 复用为 UART0 TX/RX；
4. 调用 `uart_init()`；
5. 以 9600 8N1 打开 UART；
6. 初始化动作邮箱和语音事务状态；
7. 创建独立语音工作线程。

UART 句柄在整个应用运行期间保持打开，仅在程序退出时释放。持续持有句柄可保持引脚复用、波特率和 FIFO 状态稳定。

### 7.2 节拍发送

`SendBytes()` 使用如下发送时序：

```text
send byte[0]
wait 2000 us
send byte[1]
wait 2000 us
...
send byte[n-1]
wait 30 ms after frame
```

动作帧为 10 字节，纯字节发送部分约占 18 ms，帧后保护时间为 30 ms。单次发送总开销远小于语音播放时间，并在独立线程执行，不影响 NPU 推理主循环。

### 7.3 RX 消费

语音线程每 3 ms 调用 `PumpRx()`：

1. 一次申请最多 32 字节接收缓冲区；
2. 调用 `uart_receive_data()`；
3. 对返回字节逐个执行 `HandleStatusByte()`；
4. 如果一次读满缓冲区，继续读取，最多四轮；
5. 更新 `rx_bytes` 和各状态码计数。

TX 与 RX 均由同一个语音线程管理，避免多个线程同时访问 UART 句柄。

## 8. 连续播报并发模型

### 8.1 为什么需要独立线程

视觉主循环对延迟敏感，而 UART 字节间隔、帧后保护时间和语音播放均为慢操作。如果直接在推理线程发送，可能造成：

- 采集帧延迟；
- NPU 推理间隔增大；
- OSD 更新不连续；
- 端到端延迟波动。

因此 `VoiceNotifier` 使用一个专用工作线程。主线程只提交动作，操作时间接近一次互斥锁赋值。

### 8.2 最新动作邮箱

共享邮箱字段包括：

- `pending_frame_id_`：产生动作的帧号；
- `pending_action_`：最新行动；
- `pending_key_`：动作去重键；
- `pending_ready_`：邮箱中是否有有效状态。

主线程每次更新直接覆盖邮箱，不形成 FIFO 队列。例如在语音播放期间，决策从 `clear -> slow -> stop` 连续变化，邮箱最终保留 `stop`，不会依次播放已经过期的“减速”。

### 8.3 单事务模型

同一时刻只允许一个语音事务处于活动状态。事务保存：

- 当前固定帧；
- 动作名称；
- 来源帧号；
- 发送时间；
- 序列号；
- 当前是否正在播放。

短语按帧长度设置确定性完成时间：

- 8 字节短帧预留 650 ms；
- 10 字节行动帧预留 900 ms。

正式六种语音均为 10 字节，因此按 900 ms 完成。事务完成后，线程立即重新读取邮箱。如果动作已变化，下一条发送最新动作；如果动作未变化，则等待对应重复周期。

### 8.4 不积压原则

本系统采用“覆盖”而不是“排队”：

```text
高频决策流 -> 单槽最新动作邮箱 -> 单语音事务
```

这一模型保证语音与当前环境保持一致，语音延迟上界主要由当前短语剩余时间决定，而不是由历史消息数量决定。

## 9. 持续播报策略

### 9.1 周期重复

盲人需要持续确认设备仍在工作，因此动作保持不变时也会重复播报：

| 动作 | 默认周期 |
|---|---:|
| 直行 | 1200 ms |
| 减速 | 1200 ms |
| 左转 | 1200 ms |
| 右转 | 1200 ms |
| 停下 | 1600 ms |
| 异常 | 1800 ms |

周期从上一事务完成时刻开始计算。短语播放和重复间隔共同构成用户听到的节奏。

### 9.2 动作变化

当前事务结束后，调度器优先检查动作是否变化：

```text
if latest_action != last_completed_action:
    send latest_action immediately
else if repeat_interval_elapsed:
    repeat current action
```

动作不会在一条语音中途被另一个 UART 帧截断，因此“停下”“异常”等双字短语能够完整播放。最新安全动作在当前短词结束后立即接管。

### 9.3 发送与决策频率解耦

`A1_VOICE_INTERVAL_FRAMES=2` 控制普通动作提交频率，`stop` 和 `system_fault` 不受普通帧间隔限制。提交频率只影响邮箱刷新，不等于 UART 发送频率；实际发送仍由语音事务和重复周期控制。

## 10. 异常播报机制

### 10.1 异常来源

`SystemHealth` 统一管理：

1. 摄像头取帧连续失败；
2. 镜头遮挡、全黑、过曝或平坦图像；
3. 图像采样哈希长期不变；
4. NPU 推理连续失败；
5. FPS/P95 延迟异常；
6. 可用内存过低；
7. 检测候选数量异常爆炸。

任一故障达到阈值后，`SafeDecision()` 输出 `system_fault`。此时 OSD 显示健康告警，语音统一播报“异常”。

### 10.2 摄像头遮挡判定

系统对灰度图进行稀疏采样，计算：

- 平均灰度 `mean`；
- 灰度标准差 `stddev`；
- 暗像素比例 `dark_ratio`；
- 亮像素比例 `bright_ratio`；
- 采样哈希 `sample_hash`。

判定条件：

```text
dark_cover   = mean < 38 and dark_ratio > 0.82 and stddev < 10
bright_cover = mean > 230 and bright_ratio > 0.88
flat_frame   = 0 < stddev < 2.5
```

异常证据不是简单二值状态，而是泄漏积分：

```text
bad frame  : data_fault_frames += 1
good frame : data_fault_frames = max(0, data_fault_frames - 1)
trigger    : data_fault_frames >= 8
```

这样可抑制遮挡边缘漏入少量亮光造成的状态闪烁。

### 10.3 异常独占

故障锁存期间：

- 检测框从 OSD 清除；
- 正常避障决策被 `system_fault` 覆盖；
- 语音邮箱持续写入 `system_fault`；
- `clear/slow/left/right/stop` 不能覆盖异常语音；
- 按 1800 ms 周期持续播报“异常”。

### 10.4 恢复条件

恢复采用双层滞回。

系统健康层要求：

1. capture、inference、data、frozen、resource、memory 和 candidate 指标全部归零；
2. 之后连续 30 个处理帧保持健康；
3. 才解除 `fault_latched`。

语音层要求：

1. 记录最后一次收到 `system_fault` 的时间；
2. 在其后至少 2500 ms 内继续把普通动作覆盖为 `system_fault`；
3. 保持期结束后才允许恢复正常行动语音。

因此恢复流程为：

```text
解除遮挡
 -> 异常证据逐步衰减到 0
 -> 连续 30 个健康处理帧
 -> 系统健康锁解除
 -> 语音安全保持时间结束
 -> 恢复直行/减速/转向/停下
```

## 11. 关键类与函数

### 11.1 `VoiceNotifier`

定义于 `include/voice_notifier.hpp` 和 `src/voice_notifier.cpp`。

| 函数 | 作用 |
|---|---|
| `InitializeFromEnv()` | 读取参数、打开 UART、启动线程 |
| `OpenA1UartApi()` | 配置 UART0 引脚和驱动句柄 |
| `BuildFixedPromptFrame()` | 动作到固定 SYN6288 帧映射 |
| `SendBytes()` | 按 2 ms 字节间隔发送完整帧 |
| `PumpRx()` | 持续读取 RX FIFO |
| `HandleStatusByte()` | 解析模块状态码 |
| `StartProtocolSpeech()` | 建立一个语音事务 |
| `HandleProtocolTimeouts()` | 按短语时长完成事务 |
| `WorkerLoop()` | 邮箱、RX、重复周期和发送调度 |
| `Update()` | 主线程提交最新动作并执行异常保持 |
| `Release()` | 停止线程并释放 UART/GPIO |

### 11.2 `AvoidancePlanner`

定义于 `include/avoidance_planner.hpp` 和 `src/avoidance_planner.cpp`，负责从稳定目标和测距结果生成行动。语音模块只消费规划结果，不重复实现避障规则。

### 11.3 `SystemHealth`

定义于 `demo_obstacle.cpp`，负责异常检测、锁存、恢复和安全决策覆盖，是“异常”语音的唯一上游来源。

## 12. 线程安全与生命周期

### 12.1 共享状态保护

主线程与语音线程共享的邮箱和活动事务使用 `worker_mutex_` 保护。计数器和模块状态使用原子变量，便于主线程低成本输出健康日志。

### 12.2 条件变量

`worker_cv_` 用于线程退出通知。工作线程还会按 `A1_VOICE_RX_POLL_MS=3` 定时唤醒，因此即使动作不变化，也会持续消费 UART RX 并检查重复播报时间。

### 12.3 退出流程

程序退出时：

1. 设置 `worker_stop_`；
2. 清除待处理动作；
3. 通知条件变量；
4. `join()` 等待语音线程结束；
5. 关闭 UART；
6. 释放 GPIO 句柄。

该顺序避免后台线程访问已经释放的驱动对象。

## 14. 日志设计

### 14.1 启动日志

```text
[VOICE][INFO] backend=a1_uart pins=UART_TX0/UART_RX0
[VOICE][INFO] ready ... protocol=syn6288_compat_state_machine_v2
[VOICE][INFO] ... transport=persistent_paced_duplex
[VOICE][INFO] asynchronous UART worker started
```

### 14.2 事务日志

```text
[VOICE] seq=25 TX frame=... action=turn_left bytes=10
[VOICE] seq=25 DONE source=timer duration_ms=...
```

- `seq`：语音事务序列号；
- `frame`：产生该动作的视觉帧号；
- `action`：内部行动；
- `bytes`：固定帧字节数；
- `DONE`：事务完成，可以调度下一动作。

### 14.3 健康日志

```text
[VOICE][HEALTH] frame=... state=...
current=... latest=... tx=... completed=...
rx_bytes=... recoveries=...
```

正常持续播报时，`tx` 和 `completed` 会持续增长，`latest` 与规划器当前动作一致。

## 16. 验证方案

### 16.1 基础动作

依次构造：

1. 无障碍：持续播报“直行”；
2. warning：播报“减速”；
3. 中央近障：完整播报“停下”；
4. 右侧/中央阻塞且左侧安全：播报“左转”；
5. 左侧/中央阻塞且右侧安全：播报“右转”。

### 16.2 连续性

保持单一场景至少 60 秒，确认相同动作按照重复周期持续播报。随后连续切换多个场景，确认不播放已经过期的历史动作。

### 16.3 异常闭环

1. 完全遮挡摄像头；
2. 等待异常证据达到阈值；
3. 确认 OSD/串口进入系统异常；
4. 遮挡期间持续听到“异常”，不得穿插“直行”；
5. 解除遮挡；
6. 等待健康证据归零、30 个健康帧和语音保持时间；
7. 确认恢复正常行动播报。

### 16.4 一致性

同一时刻应满足：

```text
AvoidanceDecision.action
    == OSD 顶部动作
    == 串口摘要动作
    == VoiceNotifier.latest
    == 实际中文播报语义
```

## 17. 当前成功版本的技术特征总结

当前系统实现了：

1. A1 UART0 到 SYN6288 的双向电气连接；
2. 1.8 V 与 3.3 V 安全电平转换；
3. 六种短行动的固定 GBK 协议帧；
4. 推理线程与语音线程解耦；
5. 单槽最新动作邮箱，杜绝历史语音积压；
6. 单事务顺序播放，保证“停下”和“异常”完整输出；
7. 相同动作周期重复，实现持续导航；
8. RX FIFO 持续消费和通信状态统计；
9. 摄像头遮挡等异常的检测、锁存、持续告警和延迟恢复；
10. OSD、串口和语音共享同一避障决策源。

该设计形成了从视觉感知、风险评估、行动规划到语音执行的完整闭环，满足盲人导航对实时性、简洁性、持续性和安全优先级的要求。
